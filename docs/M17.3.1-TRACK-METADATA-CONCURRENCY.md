# ReleaseCore M17.3.1 — Track Metadata Concurrency Repair

## Problem

M16.3 originally used `Release.updatedAt` for optimistic concurrency.

M17.2.1 narrowed the dedicated Track editor to `Track.updatedAt`, which was an
improvement but still too broad. `Track.updatedAt` is the timestamp for the
entire Track database row, not only the fields edited by **Track information**.

Background/internal work can legitimately update the Track row without another
human editing title, language, explicit status, lyrics, or ISRC. Examples
include delivery/catalog linkage and other operational mutations.

That means a user can reload Edit Track Info, make a legitimate metadata edit,
and still receive a false:

`This track changed since this editor loaded.`

## Repair

M17.3.1 introduces a dedicated integer revision:

`Track.metadataVersion`

It starts at `0` and changes only when Track-information metadata changes.

The dedicated Track editor sends:

`expectedTrackMetadataVersion`

The server atomically claims the version with:

- `WHERE metadataVersion = expected`
- `metadataVersion = metadataVersion + 1`

before committing the Track-information save.

This removes timestamp precision and unrelated Track-row activity from the
concurrency contract.

## What counts as Track metadata

The metadata revision advances for:

- title
- version/subtitle
- language
- explicit status
- lyrics
- ISRC assignment/correction

ISRC writes from the shared ISRC service also increment the metadata revision so
a genuine concurrent ISRC change is still detected.

Artist assignments, contributor credits, master-file operations, Shopify
product linkage, previews, and other operational Track activity do not advance
this metadata revision.

## Bulk editor

The multi-track Bulk Editor continues using `Release.updatedAt` because track
reordering and multi-row atomic edits need release-wide concurrency.

## Migration

`20260904193000_m17_3_1_track_metadata_version`

Existing Tracks receive metadataVersion `0`.
