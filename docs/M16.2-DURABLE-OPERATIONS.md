# ReleaseCore M16.2 — Durable background operations

M16.2 moves the highest-latency Shopify/distribution operations out of the merchant's browser request and into a durable PostgreSQL-backed operation queue.

## Backgrounded operations

- audio preview generation;
- targeted Sync Health recovery;
- release-level storefront publication orchestration;
- Shopify track product creation/sync;
- Album/EP parent product and bundle sync;
- legacy per-product publication actions if invoked.

Short identifier edits remain synchronous.

## Durability model

Each `OperationJob` records:

- tenant shop;
- deployment profile;
- release;
- operation intent;
- deterministic operation fingerprint;
- request idempotency key;
- payload;
- `QUEUED`, `RUNNING`, `SUCCEEDED`, or `FAILED` status;
- attempt count and maximum automatic attempts;
- availability / lease timestamps;
- safe last error;
- result;
- start/completion timestamps.

`OperationJobAttempt` stores individual attempt history.

## Idempotency and concurrency

The queue reuses:

1. a previous job with the exact merchant-supplied idempotency key; or
2. an already `QUEUED`/`RUNNING` job with the same operation fingerprint.

This prevents double clicks, browser retry behavior, and multiple app replicas from concurrently starting the same active operation.

The worker uses an atomic `updateMany` claim after selecting a candidate. Database partial unique indexes also enforce active fingerprint deduplication and same-release operation serialization, so separate Railway replicas cannot mutate the same release concurrently.

## Worker lifecycle

Production remains one Railway service per ReleaseCore deployment.

`docker-start` now runs `scripts/start-production.mjs`, which starts:

- the existing React Router web process; and
- a lightweight operation-worker process.

The supervisor generates an in-memory random worker secret for each container. The worker only talks to the local web process at `/internal/operation-jobs/drain`. The internal endpoint uses constant-time secret comparison and is not accessible without that runtime-only secret.

No new Railway secret is required.

## Failure/retry behavior

- 5xx/network failures are automatically retried up to the current job maximum.
- HTTP 408 and 429 are retryable.
- normal 4xx workflow/preflight errors fail immediately so a merchant can correct the release instead of creating a retry loop.
- manual Retry from Distribution gives a failed job another three-attempt budget.
- a `RUNNING` lease older than 45 minutes is abandoned and safely requeued.
- terminal failures are also written to the existing Sync Health failure history.

## UI

Distribution shows recent Background operations with:

- current status;
- attempt count;
- last safe error;
- recent attempt history;
- manual Retry on failures.

The UI polls the lightweight operation-job endpoint while work is active and performs one full Distribution revalidation when the queue becomes idle.

Operations Center now includes active background-job count and failed-operation issues.

## Existing notifications

`NotificationDelivery` already has durable status/attempt/error fields and remains independent. M16.2 does not collapse notification delivery into the release-operation queue.

## Deployment

This milestone includes a Prisma migration. Railway's existing `npm run setup` executes `prisma migrate deploy` before the supervised production runtime starts.

No Shopify scopes, extensions, TOML configuration, or Shopify app version deployment changes are required.
